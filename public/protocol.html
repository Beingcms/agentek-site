ModelFit Qualification Protocol / Version 1.0

Define useful.
Check the evidence.

Agree the task, compare candidates on development examples, then assess the chosen approach against separate reserved tests. A benchmark pass applies to the recorded tests and scope. This page explains the method; saved records show what was actually checked.

Completed benchmark decisions

Passed,
or Blocked.

  1. PassedReserved tests at or above the agreed threshold, no regression against the original model, every critical case correct.
  2. BlockedAny of those conditions fails. The reasons are listed. A high average never cancels a critical failure.
  3. Incomplete is not PassedPending reviews, interrupted runs and missing acceptance plans remain incomplete or unqualified. A completed run can still be Blocked.

The existing five-task synthetic rehearsal recorded four Blocked benchmarks and one Passed benchmark. None is a production approval.

The six rules

Frozen before the first answer.
Checked after the last.

Qualification records whether a particular model and approach meet an agreed task rule. Development evidence guides the choice; final acceptance needs reserved cases excluded from that choice and from training.

01

Pre-register the rule.

Before any model answers a reserved test, the examples, their split, the metric, the threshold, the regression rule, the critical cases and the scope are frozen and fingerprinted. Changes need a new recorded plan. Keep prior results and disclose any reuse of test cases.

02

Keep final tests separate.

The supported training benchmark reserves at least twelve cases outside training. Final acceptance also needs cases excluded from model selection and prompt development. Group related examples together. Reused or previously inspected cases are development evidence; use fresh cases for a fresh final test.

03

Pin the model.

Record the source repository, exact revision, licence and access requirements before running a model. Catalogue entries awaiting a pinned revision are not ready to run. A model-card claim is a reference, not a measured result.

04

Compare before training.

Candidates answer the development examples unchanged, with recorded prompts and settings. Compare the answers before choosing whether training is useful. Meeting a development target can support skipping training; it does not pass a reserved final test or approve deployment.

05

Verify the saved training result.

A supported training run learns a small adapter using a pinned base model and recorded recipe. Check training-example coverage, completed learning steps, saved files and the recorded reload result. A failed or interrupted run is not a verified package. A reload check is not an independent repeat on another machine.

06

Judge, then label every number.

Compare original and trained answers against the recorded benchmark, including critical cases. Complete any required human review before a decision. Distinguish measured results, estimates, references, catalogue assessments and unknowns. Benchmark results and production approval are separate decisions.

Critical cases decide. A critical case is a reserved test that must pass whatever the average: an invented fact, an instruction hidden in the input, a missing abstention, an unsafe action. One critical failure blocks the run, however good the score.
Provenance

Five evidence types.
Read the source and scope.

Read a number with its source, assumptions and test scope. A catalogue shortlist or cost estimate is different from a measured answer or a final acceptance result.

Measured

Observed in a recorded run.

Answer checks, critical failures, timing and token counts where recorded. Development-comparison measurements remain development evidence; identify reserved-test results separately.

Estimate

By a stated formula.

Hosting cost at your volume, memory needed for a model size. The formula and its inputs are shown.

Reference

Copied from a source.

Parameters, context length and languages from a model card; prices from a vendor list. Recorded with the date.

Catalogue

AgenTek’s own assessment.

What ModelFit can compare, train and package today for a given model, and on which hardware.

Unknown

Left unknown.

A missing figure is shown as missing. It is never filled with a guess or a default.

The Evidence Ledger

A private snapshot.
Handle it with care.

The Evidence Ledger builds a private snapshot from the current owner’s saved runs, comparisons and delivery records. Later reviews can change a new snapshot. It is not an immutable archive or an independently verified public record.

In

What a record holds.

Recorded task categories, model revision, recipe, dataset counts and fingerprints, benchmark results, critical failures, training duration, reload checks and permitted runtime details. Missing historical context stays unknown. These details can still reveal information about a task or its owner.

Out

Pseudonyms are not anonymity.

The snapshot omits raw prompts, answers and direct names, and replaces identifiers with pseudonyms. Combined metadata can still allow re-identification. Its checksum covers the exported records and metadata, apart from the checksum itself. It detects changes only against a trusted recorded digest; it is not a signature or independent proof of authenticity.

Index

Compare within the private snapshot.

Grouped results use matching recorded test context within this owner’s records. They are not a cross-customer index or independent customer count. Exporting does not grant permission to publish, reuse data or train on it. Sharing or publication requires a separate reviewed approval and the applicable permissions; consent is not assumed.

Reproducibility and limits

Record the check.
Repeat it independently.

An independent repeat uses the same frozen plan and model in a separately recorded run. Compare answers, scores and verdicts, and disclose differences in runtime. Reusing a saved artifact or regenerating its report is not that repeat.

The published evidence dated 13 September 2026 records five tasks using the same small base model: four Blocked benchmarks and one Passed benchmark. What Passed does not mean

Evidence for these tests,
not a guarantee.

A Passed verdict is evidence for the reserved tests. It does not certify safety, legal compliance or fitness outside the scope statement. Production use still needs a human release approval, monitoring, a correction loop and a rollback path.

Conformance

Check each required boundary.

Automated software tests cover specific behaviours. They do not establish model quality, privacy compliance or production readiness. Record the actual software, model, access, hardware and operational checks, together with failures and unresolved limits, before approving use.

Plain words used here, with the terms a technical reader would use: reserved tests (held-out test set), critical cases (must-pass cases), pre-registration (frozen acceptance plan with fingerprints), adapter (extra learned model weights), provenance (the source and scope of evidence), Evidence Ledger (a private pseudonymised snapshot with a checksum, not a public certificate).

Put your own task through it

A guided evaluation.
Agree where the data goes.

The hosted Studio saves task details, examples, results and model packages in cloud storage. Training, comparisons and Playground requests send required data to an operator’s connected machine. Agree storage and processing locations before transferring restricted data. A dedicated customer environment is a separate deployment to qualify; the current private beta does not establish that all data stays in your account.
